**`motortest` numbering:** MAVProxy `motortest N` numbers motors by **test order**, not motor number. Test order runs clockwise from front-right: 1 = M2 (FR), 2 = M1 (BR), 3 = M3 (BL), 4 = M4 (FL).

## 6. Issues found and fixed (tools and environment only)

1. **`waf` used Homebrew Python, which has no empy:** `/opt/homebrew/bin` had been prepended to PATH *after* venv activation. Fixed by activating the venv last.
2. **DroneCAN DSDL generator stuck in a respawn loop (Python 3.14):** `dronecan` imports `pkg_resources`, but 3.12+ venvs ship without setuptools. Each `multiprocessing` worker failed its import and was respawned forever, producing 0 files. Fixed with `pip install "setuptools<81"` in the venv; setuptools ≥ 81 drops `pkg_resources`.
3. **MAVProxy failed to start:** it needs `gnureadline` on macOS, which is in ArduPilot's macOS prerequisites list. Installed in the venv.
4. **No JSON sensor data from Gazebo:** `ArduPilotPlugin` always subscribes to the IMU's *default* scoped topic, `scopedName(imu) + "/imu"` (`ArduPilotPlugin.cc:1165`), and ignores a custom `<topic>`. `make_sitl_world.py` therefore removes `/airmouse/imu` in **SITL worlds only**. The baseline is unchanged.
5. **MAVProxy commands ignored:**
   - `--non-interactive` stops MAVProxy reading stdin, so that flag was removed.
   - The script must keep reading MAVProxy output. Otherwise the pty fills and the `motortest` commands are not processed (INFERRED from the all-zero run before the fix).
6. **ardupilot_gazebo upstream CMake requires OpenCV and GStreamer** for `GstCameraPlugin`. To avoid a large Homebrew install, only `ArduPilotPlugin` is built, from unmodified sources.

**What happened (OBSERVED):**

1. EKF3 reached "using GPS", GUIDED mode was set, and arming succeeded (`COMPONENT_ARM_DISARM: ACCEPTED`). `takeoff 1.5` was accepted.
2. The vehicle climbed fast. The first Gazebo truth sample at or above the target read **z = 2.20 m**, against a target of 1.54 m.
3. It then **flipped in pitch**, with roll staying controlled:
   - IMU pitch rate GyrY reached −143 to −155 °/s.
   - ATT roll and pitch swung through ±180°.
   - The motor outputs saturated, split front/back: front motors C2/C4 ≈ 1947–1949 µs, rear motors C1/C3 ≈ 1150–1224 µs. The controller was demanding nose-up while the measured rate kept going nose-down, which is **positive feedback on pitch**.
4. About 0.4 s later, ArduCopter SITL **crashed** with `SIGILL` (EXC_BAD_INSTRUCTION) in `EKFGSF_yaw::predict` ← `NavEKF3_core::UpdateFilter` ← `AP_AHRS::update_EKF3`. This is most likely ArduPilot's floating-point-exception trap on non-finite values during the tumble (INFERRED). It is a consequence of the flip, not its cause.
5. Because of lock-step, Gazebo sim time stopped and the test script hung. That was a tool bug, now fixed: there are wall-clock limits, and the script detects a SITL exit.

**Root cause: IMU frame convention in the SITL world.** This is a configuration error in `make_sitl_world.py`, not gains or physics.

- `ArduPilotPlugin.cc:1732-1750` (SOURCE-CODE VERIFIED) passes the IMU's linear acceleration and angular velocity to SITL **unchanged** and assumes the IMU is already in the aircraft frame: x forward, y right, z down (FRD). The reference iris model therefore mounts its IMU sensor with `<pose degrees="true">0 0 0 180 0 0</pose>`.
- The AirMouse IMU has no sensor pose, so it reports in the model frame, FLU. ArduPilot therefore received y and z axes with the **wrong sign**:
  - pitch rate and yaw rate were inverted, which gives the pitch runaway; yaw is slower, with low authority
  - roll rate was correct, which is why roll stayed controlled
- At rest the dataflash log shows `IMU AccZ = +9.817 m/s²`. A correctly oriented FRD accelerometer reads −9.81 at rest (OBSERVED).
- The motor map was **not** the cause: motortest verified the positions and spin directions (§4).

**Proposed fix, not applied, awaiting approval to re-fly:** in **SITL worlds only**, `make_sitl_world.py` adds `<pose degrees="true">0 0 0 180 0 0</pose>` to the IMU sensor, exactly as in the iris reference. This changes only the sensor's reporting frame. There are no physics, gain or baseline changes. The baseline IMU keeps FLU and its Stage 10 checks.

1. On the ground, the logged `IMU AccZ` should be about −9.81 and ATT should be level.
2. A hand-checked rate sign: tilt the model with `set_pose` and check the GyrY sign.
3. Only then repeat takeoff 1.5 m, hover 30 s and land.

### 9.4 Hover throttle and `MOT_THST_HOVER` learning

- **Learning did not run in either flight.** The learned value equals the initial 0.5400 (read back after disarm), and dataflash CTUN `ThH` is 0.5400 throughout (OBSERVED).
- **Why (SOURCE-CODE VERIFIED, `ArduCopter/Attitude.cpp:29-58`):** `update_throttle_hover()` returns early unless the desired vertical velocity is *exactly* zero (`is_zero(pos_control->get_vel_desired_cms().z)`). In GUIDED position hold, the logged desired vertical velocity (PSCD.DVD) is **1.29e-5 m/s on all 200 hover samples, never exactly zero** (OBSERVED). Learning therefore needs an ALT_HOLD or LOITER hover with neutral sticks. That is a test-procedure decision for Rohit.
- **Actual hover throttle, thrust domain:** CTUN `ThO` = **0.4877** in both worlds (OBSERVED).
- **Comparison with the analytical values:**
  - The raw thrust fraction needed at hover is **0.5319**, using MOT_SPIN_MIN/MAX 0.15/0.95 with EXPO 1 (`AP_Motors_Thrust_Linearization.cpp:101-130`). It would be 0.538 with spin limits 0/1.
  - ArduPilot multiplies `ThO` by a compensation gain (`get_compensation_gain()`, `:186-202`): 1/lift_max for the battery, times 1/air-density ratio.
  - Battery: SITL 12.6 V / `MOT_BAT_VOLT_MAX` 12.8 V gives lift_max = 0.969, i.e. ×1.032 (ANALYTICAL).
  - The remaining factor implied by the data, 0.5319 / 0.4877 / 1.032 = 1.057, corresponds to an air-density ratio of about 0.946. That is ISA density at the 584 m AMSL SITL home (INFERRED; ArduPilot's exact density estimate was not checked).
- **Interpretation:** a learned `MOT_THST_HOVER` would converge to about **0.488** at this SITL home altitude and battery voltage, not 0.538 or 0.532 (INFERRED).

**Does ArduPilotPlugin forward rangefinder data over JSON? Yes (SOURCE-CODE VERIFIED).**

- `ArduPilotPlugin` takes `<sensor><type>…</type><index>N</index><topic>…</topic></sensor>` entries, subscribes to them as `gz.msgs.LaserScan` (`ArduPilotPlugin.cc:895-1000`), and latches the **minimum** range of each scan. No return (inf) becomes `2 × range_max`.
- It sends `rng_1…rng_6` in the JSON packet (`:1965-1995`). SITL parses them into `rangefinder_m[]` (`SIM_JSON.cpp:389`), and the SITL rangefinder driver (`RNGFND1_TYPE 100`, `AP_RangeFinder_SITL.cpp`) reads them.
- `make_sitl_world.py` now adds `<sensor><type>RANGEFINDER</type><index>1</index><topic>/airmouse/rangefinder</topic></sensor>`.
- The ArduPilot side is in `simulation/sitl/airmouse_provisional_rangefinder.parm` (PROVISIONAL): `RNGFND1_TYPE 100`, `ORIENT 25` (down), `MIN_CM 20`, `MAX_CM 800`, `GNDCLEAR 1`.

### 10.3 Step 2b: ExternalNav plumbing stub — GROUND-TRUTH-DERIVED, PLUMBING TEST ONLY

> **GROUND-TRUTH-DERIVED, PLUMBING TEST ONLY.** `tools/externalnav_stub_GROUND_TRUTH_PLUMBING_ONLY.py` fabricates odometry from the Gazebo ground-truth pose plus synthetic noise and drift. It exists only to exercise ArduPilot's ExternalNav path in SITL. It **must be removed once Doshi's SLAM odometry exists**, and it must **never** be used as the navigation solution or in any performance claim. The same label appears in the stub's file name, its docstring, every line of its log output, its CSV header and the parameter file.

**Message:** MAVLink `ODOMETRY` at 30 Hz from component 197 (VIO) to SITL TCP 5762.

- `frame_id` is `MAV_FRAME_LOCAL_FRD` and `child_frame_id` is `MAV_FRAME_BODY_FRD`. These are the only frames ArduPilot 4.6.3 accepts (SOURCE-CODE VERIFIED, `GCS_Common.cpp:3876-3910`).

**What the truth data shows:** the maximum horizontal excursion during the loss was **1.6 cm**, and attitude stayed small (roll/pitch peaks 0.16°). The SITL has no wind and clean IMU noise, so dead-reckoning drift here greatly understates real drift (INFERRED).

**Why no failsafe (SOURCE-CODE VERIFIED, `ArduCopter/ekf_check.cpp:29-75, 140-165`):**

- Copter's EKF failsafe fires when the velocity, position or compass **variances exceed `FS_EKF_THRESH`** (two of them, or velocity at 2× the threshold), **or** when the EKF reports **no position estimate**.
- With no aiding measurements there are no innovations, so the logged test ratios dropped to zero.
- The EKF kept reporting a position estimate while dead-reckoning (INFERRED from the absence of a failsafe).

**SAFETY FINDING for Rohit:** with default parameters, a loss of the SLAM/ExternalNav feed did **not** trigger any failsafe within at least 25 s of "stopped aiding". The vehicle kept LOITERing on dead-reckoning, which on real hardware would drift. Options to decide on, none applied:

- (a) a companion-side watchdog. Doshi's node stops publishing → it commands LAND or ALT_HOLD.
- (b) an onboard Lua script that monitors VISO health (`PreArm: VisOdom: not healthy` shows ArduPilot tracks it) and changes mode.
- (c) a secondary EKF source set, for example optical flow (`EK3_SRC2_*`), with source switching.
- (d) review `FS_EKF_THRESH` and the EKF3 dead-reckoning limits.

These need verification in SITL with a drifting IMU or wind (`SIM_WIND_*`, `SIM_ACC*_BIAS`), which would make the dead-reckoning drift realistic.
